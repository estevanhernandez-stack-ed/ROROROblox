- [x] **6. End task ends RoRoRo; the X still hides it** (hard)
  Spec ref: `board.md > Tier 2 > 5`; `src/ROROROblox.App/MainWindow.xaml.cs` (`OnClosing`); `MainWindow.xaml` (`ui:TitleBar ... ShowClose="True"`, WPF-UI 4.3.0); `App.RequestShutdown`
  What to build: Tell a close that came from outside the process from one made inside it, and **fail towards hiding**. Revised 2026-11-16 before dispatch: the first draft marked user closes by watching for `SC_CLOSE`, which would have made any in-app close it missed quit the app. The rule now identifies the external case positively. An outside tool (`taskkill` without `/F`, Task Manager's End task) posts `WM_CLOSE` to the window, so it arrives through the message queue. Every in-app close (`Window.Close()`, Alt+F4, the taskbar's Close, the title bar's X) reaches the window as a `WM_CLOSE` that is sent, not queued. So: (a) a small helper watches the UI thread's queued messages (`ComponentDispatcher.ThreadFilterMessage`) and notes when a queued `WM_CLOSE` is addressed to the main window. (b) A pure function decides: shutting down means proceed; an external close means quit; anything else means hide to tray, as today. (c) `OnClosing` still calls `SaveWindowPlacement()` first. On an external close it cancels this close, hides, logs one Information line, and asks the app to quit through the same path the tray's Quit uses (`App.RequestShutdown`), posted to the dispatcher so `Close()` is not re-entered. (d) The note does not outlive the close it belongs to, and the hook is removed when the window closes. A `WM_CLOSE` posted while a native modal loop is running (a menu, a move or size drag) is not seen by the filter and so hides: that is the safe default and is accepted. Size M.
  Acceptance: Done when tests show: the decision table (three rows); on a real window on an STA thread with a pumping dispatcher, a `WM_CLOSE` delivered with `PostMessage` is classified external, while `Window.Close()`, and `WM_SYSCOMMAND/SC_CLOSE` delivered with `SendMessage`, are classified internal; a posted `WM_CLOSE` for a different window on the same thread is not classified external for this one; the note is cleared after one close, so an internal close that follows an external one hides; the title bar's X is shown to be an internal close, by a test that drives a real `ui:TitleBar` if the rendering test host allows it, or else by evidence from the WPF-UI 4.3.0 assembly named in the report plus a source fence. `WindowChromeFenceTests`, `ModalDefaultButtonSafetyTests` and the button fences still pass.
  Verify: the full unit project, `dotnet test src/ROROROblox.Tests/ -c Release --no-build`.
